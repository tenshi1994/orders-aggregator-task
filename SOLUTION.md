# Решение

## Что сделано

### 1. Скидки в статистике

- Миграция `002_amount_paid.sql`: колонка `orders.amount_paid_kop`. `NULL` - строка сохранена до появления скидок в API.
- `OrdersService.normalize` принимает `amountPaid`.
  Если поля нет (у заказов, созданных до 15.03, его нет совсем) - скидки нет (`amountPaid = amount`).
- `daily-totals` отдаёт `{ date, total, gross, discount, net }`. Всё суммируется в целых копейках,
  в рубли переводится только в ответе.

### 2. Жалоба по c_7 - причина и исправление

**Причина.** `TotalsService.daily` брал смещение таймзоны клиента один раз - на момент запроса - и применял его ко всем заказам.
У `c_7` таймзона `Europe/Berlin`, 29.03 в 01:00 UTC Берлин перешёл с UTC+1 на UTC+2. Запрос делается зимой, поэтому для заказов после перехода
бралось смещение +1 вместо +2, и заказы, созданные в 22:00–23:00 UTC, попадали на предыдущий день.
27–28.03 ещё зимние - там всё сходилось. Результат к тому же зависел от даты запроса: летом ломались бы зимние дни.

**Как нашёл.** Выгрузил все заказы из API и для заказов `c_7` за 26.03–01.04 сравнил дату при смещении
«на сейчас» и при смещении на момент заказа: расходятся ровно заказы около полуночи начиная с 29.03.

**Исправление.** `dateInTimeZone(at, timeZone)` (`utils/time.ts`) считает календарную дату через `Intl`
со смещением на сам момент заказа. `TotalsService` раскладывает по дням каждый заказ через неё.

### 3. Что ещё исправил по ходу (влияет на результат)

- **Потеря копейки в `toKop`.** `Math.floor(rub * 100)` в double: `4723.9 * 100 = 472389.99999999994` → 472389.
  Пока все `amount` были целыми, это не проявлялось.
  Теперь доли копейки отбрасываются по десятичной записи числа.
- **Гонка при применении версии заказа.** `apply` читал заказ и потом сохранял.
  Мок шлёт вебхуки параллельно (до 6 одновременно), с дублями и не по порядку, поэтому старая версия
  могла перетереть новую. Теперь проверка "версия новее" - в самом upsert
  (`ON CONFLICT ... DO UPDATE ... WHERE orders.updated_at < excluded.updated_at`).
  Тест на старом коде падал стабильно (5 из 5 прогонов), на новом проходит.
- **Существующие данные.** После миграции у старых строк `amount_paid_kop = NULL`, а повторный синк
  вернул бы `stale` (updatedAt тот же) и не дозаполнил бы их. Upsert обновляет такие строки и той же версией -
  один раз. Пока строка не дозаполнена, она считается без скидки.

## Как проверял

1. `npm run typecheck`, `npm test` - 37 тестов (было 27). Новые:
   скидки (пример из задания, заказы без полей скидки, строки, суммы на границе точности double),
   день по смещению на момент заказа (тест на два заказа по разные стороны перехода - старый код ошибается
   хотя бы на одном в любое время года), параллельные вебхуки, дозаполнение старых строк.
   В трёх старых тестах `daily-totals` `toEqual` заменён на `toMatchObject` - в ответе появились новые поля.
2. Убедился, что новые тесты ловят старые баги: подкладывал исходные версии `money.ts`, `totals.ts`,
   `services/orders.ts` + `repositories/orders.ts` - соответствующие тесты падают.
3. `result.json` - по процедуре из задания: `docker compose down -v && up -d`, `POST /sync`
   (`pages 52, received 5030, invalid 0`), вебхуки (92, все 200), запрос `daily-totals`.
4. Независимо от кода сервиса: заново выкачал все заказы из API, перехватил поток вебхуков на свой порт, 
   взял последнюю версию каждого заказа по `updatedAt`, разложил по дням через `Intl` в `Europe/Berlin` - совпало с `result.json` до копейки.
   Все 140 заказов `c_7` в БД совпали с последними версиями.
5. Идемпотентность: повторные вебхуки и `/sync` (`stale: 5030`) - ответ не изменился.

## Что заметил в коде и в поведении API

- У заказов до 15.03 нет `discountPercent` и `amountPaid`.
- `amountPaid` во всех заказах согласован с `amount × (1 − discountPercent/100)`.
- Скидка заказа меняется между версиями (3% → 10% → 33% при статусе `paid`) - `amount_paid_kop` надо обновлять вместе с версией.
- Rate limit иногда приходит как `200 { "error": "rate_limited" }`. Конец выдачи - пустая страница с тем же курсором.

## Допущения

- `net` - сумма `amountPaid` (факт оплаты), а не пересчёт из `discountPercent`.
- Нет `amountPaid` - скидки нет.
- Доли копейки отбрасываются, как и раньше в `toKop`.
- День заказа - по `createdAt` в таймзоне клиента, как было.

## Что бы доделал

- Агрегацию по дням в SQL (`created_at AT TIME ZONE tz`, `GROUP BY`) вместо выборки всех заказов в память.
- Ограничение длины диапазона `from..to`.
- Обновление закэшированной таймзоны клиента (сейчас берётся из API один раз навсегда).
- Предупреждение в логах, если `amountPaid` расходится с `amount` и `discountPercent` или больше `amount`.
